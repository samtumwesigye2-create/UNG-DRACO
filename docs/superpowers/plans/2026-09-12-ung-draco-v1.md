# UNG-DRACO V1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a production-oriented UNG-DRACO V1 service that preserves the approved ISR workflow while using PostgreSQL, JANUS-backed RBAC, audit controls, explainable detection/fusion, sanitized UNG events, and a resilient field agent.

**Architecture:** A versioned FastAPI service persists authoritative state in PostgreSQL and delegates collection, entity extraction, detection, fusion, watches, intelligence products, security, auditing, and event publication to focused modules. Protected human-source identity remains isolated inside DRACO; downstream UNG systems receive sanitized events through the HEPHA/PULSAR adapter boundary.

**Tech Stack:** Python, FastAPI, SQLAlchemy 2.x, PostgreSQL, Alembic, Pydantic 2, httpx, pytest, Docker.

**Spec:** `docs/superpowers/specs/2026-09-12-ung-draco-design.md`

## Global Constraints

- System identity is `UNG-DRACO — Detection, Reconnaissance, Analysis, Collection & Observation`.
- PostgreSQL is authoritative storage; production must not depend on SQLite.
- Every non-health endpoint requires JANUS-backed authentication/RBAC.
- Human-source identity must never appear in normal operational API responses or outbound backbone events.
- Significant state transitions carry a `correlation_id` and append an audit record.
- Outbound events use the approved `draco.*` families and are sanitized before publication.
- No autonomous lethal or weapon-control functionality is in V1.
- DRACO is not operationally certified until live acceptance passes against a deployed service and PostgreSQL instance.
